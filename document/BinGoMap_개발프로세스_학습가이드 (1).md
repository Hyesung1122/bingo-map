# 📘 BinGo Map 개발 프로세스 학습 가이드

시작부터 완성까지 프로젝트가 어떤 순서로 흘러가는지, **우리가 지금 어디에 있고 무엇을 해야 하는지** 정리한 문서입니다.
현업에서도 거의 같은 흐름으로 진행하니, 용어와 순서를 함께 익혀두세요.

---

## 0. 한눈에 보기

```
① 기획·설계 → ② 개발 → ③ 통합(머지) → ④ 통합 테스트 → ⑤ 종합 테스트 → ⑥ 릴리즈 → ⑦ 유지보수
                                             ↑ 지금 여기 (ver2)
```

| 단계 | 한 줄 요약 | 일본어 표현 (참고) |
|---|---|---|
| ① 기획·설계 | 무엇을 만들지 정하고 화면·DB를 설계 | 要件定義・設計 |
| ② 개발 | 각자 맡은 기능을 만들고 혼자 돌려봄 (단위 테스트) | 開発・単体テスト |
| ③ 통합 | 각자 만든 코드를 main에 합침 | マージ |
| ④ 통합 테스트 | 합친 뒤 기능끼리 잘 연결되는지 확인 | 結合テスト |
| ⑤ 종합 테스트 | 실제 사용자처럼 처음부터 끝까지 써보며 완성도 확인 | 総合テスト |
| ⑥ 릴리즈 | 완성본 확정 + 버전 태그 | リリース |
| ⑦ 유지보수 | 배포 후 발견된 오류 수정, 기능 추가 | 保守 |

## 1. 지금 해야 할 일 (현재: ④ 통합 테스트)

팀원들의 작업을 합친 **ver2** 상태에서, 합치고 나니 "내 로컬에서는 안 되는 것"이 나오는 게 정상입니다. 이걸 찾아서 고치는 단계예요.

### 해야 할 일
- [ ] 최신 main을 pull 받아서 **깨끗한 상태로 실행**해보기
- [ ] 안 되는 것을 발견하면 개발일지에 `[버그]`로 기록 (증상 / 에러 로그 / 재현 방법)
- [ ] 원인 확인 — 대부분 아래 셋 중 하나
  - DB 스키마 불일치 (테이블·컬럼 변경이 내 DB에 반영 안 됨) → `[환경]`
  - 설정/경로 차이 (`application.yml`, 업로드 경로 등) → `[환경]`
  - 코드 충돌·로직 오류 → `[버그]`
- [ ] 수정 → 커밋 → PR → merge
- [ ] **재테스트**: 고친 곳뿐 아니라 주변 기능도 다시 확인 (고치다 다른 걸 깨뜨리는 일이 흔함)
- [ ] 개발일지의 `[버그]`가 모두 "완료"가 되면 팀장에게 알리기
- [ ] 안정화되면 **v0.2 태그** 달기 (팀장이 진행)

### 이 단계가 끝나는 기준
기능 간 연결이 막힘없이 돌아가고, 남은 `[버그]`가 없거나 사소한 것뿐일 때

### 로컬 환경 체크 (안 될 때 먼저 확인)
| 항목 | 기준 |
|---|---|
| IDE | IntelliJ IDEA |
| Java | 17 |
| Spring Boot | 4.1.1 |
| Build | Gradle (변경 후 새로고침) |
| DB | Oracle Database 11g (11.2.0.1.0, 64-bit) |
| 확인 쿼리 | `SELECT * FROM v$version;` |

## 2. 앞으로 해야 할 일

### ⑤ 종합 테스트 (통합 테스트 통과 후)
- [ ] **시나리오 표 작성** (아래 예시를 빙고맵 기능에 맞게 늘리기)
- [ ] 팀원끼리 **서로 남의 기능을 테스트** (만든 사람은 자기 코드의 약점을 잘 못 봄)
- [ ] 시나리오마다 OK/NG 표시 → NG는 `[버그]`로 기록 → 수정 → 재테스트
- [ ] 끝나는 기준: **모든 시나리오 OK**

| 시나리오 | 확인 내용 |
|---|---|
| 회원가입 → 로그인 | 유효성 검사, 중복 처리, 잘못된 입력 |
| 지도에서 쓰레기통 찾기 | 위치 표시, 주변 맛집 연동 |
| 맛집 리뷰 작성 + 이미지 3장 업로드 | 저장, 이미지 표시 |
| 즐겨찾기 등록/해제 | 상태 반영 |
| 쓰레기통 제보 | 관리자 화면에서 확인 가능한지 |
| 예외 상황 | 빈 값, 큰 파일, 로그인 안 한 상태 접근 |

### ⑥ 릴리즈
- [ ] 종합 테스트 통과한 코드를 main에 확정
- [ ] **버전 태그** 달기
  ```bash
  git tag -a v1.0.0 -m "최종 릴리즈"
  git push origin v1.0.0
  ```
- [ ] GitHub **Releases**에 릴리즈 노트 작성 (추가된 기능 + 해결한 `[버그]`)
- [ ] README 최종 정리 (설치·실행 방법, 환경 정보, 화면 캡처)
- [ ] 개발일지를 태그별로 분리 정리
  - `[버그]` → 결함 목록
  - `[결정]` → 설계 결정 기록
  - `[배움]` → 회고 자료 (포트폴리오에 활용 가능)

### ⑦ 유지보수
- [ ] 릴리즈 후 발견된 오류는 이슈 등록 → 수정 → **v1.0.1**
- [ ] 기능을 더 추가하면 **v1.1.0**

## 3. 테스트 3종류 구분하기

| 종류 | 확인하는 것 | 누가/언제 |
|---|---|---|
| **단위 테스트** | 내가 만든 기능 하나가 혼자 잘 돌아가는가 | 개발하면서 각자 |
| **통합 테스트** | 기능끼리 연결했을 때 문제가 없는가 | 머지 후 (지금) |
| **종합 테스트** | 요구사항대로 완성됐는가 (사용자 시점 전체 시나리오) | 통합 테스트 통과 후 |

> **재테스트(회귀 테스트)**: 버그를 고칠 때마다, 고친 곳이 다른 기능을 깨뜨리지 않았는지 다시 확인하는 것. 모든 단계에서 반복돼요.

## 4. 개발일지 작성법 (문서는 하나로 통합)

개발일지 **하나**에 시간순으로 쓰고, 태그로 구분해두었다가 나중에 필요한 것만 뽑아서 정리합니다.

### 태그
```
[버그]  증상, 재현 방법, 원인, 상태
[환경]  DB 스키마, 설정 파일, 경로 등 PC마다 다른 것
[결정]  왜 이렇게 하기로 했는지
[TODO]  다음에 할 일
[배움]  새로 알게 된 것, 에러 해결 팁
```

### 작성 예시
```markdown
## 2026-09-28
- [버그] 리뷰 작성 시 500 에러 / 원인: TB_REVIEW 컬럼 불일치 / 상태: 수정중
- [환경] 업로드 경로가 팀원별로 다름 → yml 기준값 정해야 함
- [TODO] DB 변경 스크립트 팀원에게 공유
```

### 규칙
- **한 줄에 태그 하나**, 한 항목은 한 줄로 끝나게
- **날짜별 소제목(`##`)** 유지
- 상태가 바뀌면 새 줄을 쓰지 말고 **그 줄을 고치거나 `→ 완료`로 덧붙이기** (안 그러면 완료/미완료 구분이 안 됨)
- 나중에 `[버그]`로 검색하면 결함만 한 번에 모임

## 5. 버전 번호 이해하기

형식: **`v메이저.마이너.패치`**

| 자리 | 올리는 경우 | 예 |
|---|---|---|
| 메이저 (x.0.0) | 구조가 크게 바뀔 때 | v1.0.0 → v2.0.0 |
| 마이너 (0.x.0) | 기능이 추가될 때 | v1.0.0 → v1.1.0 |
| 패치 (0.0.x) | 버그 수정만 했을 때 | v1.1.0 → v1.1.1 |

### 우리 프로젝트에 적용하면
| 시점 | 버전 | 의미 |
|---|---|---|
| 개발 후 첫 머지 | v0.1 (ver1) | 기능이 처음 합쳐진 상태 |
| 통합 테스트 수정 반영 | v0.2 (ver2) | **지금 여기.** 아직 완성 전 |
| 종합 테스트 통과 | v1.0.0 | 첫 정식 완성본 |
| 이후 버그 수정 | v1.0.1 | 패치 |
| 기능 추가 | v1.1.0 | 마이너 |

> v1.0은 "처음으로 남에게 보여줄 수 있는 완성본"이라는 뜻이라, 종합 테스트 전에는 1.0 미만으로 둡니다.
> 버전은 이름만 붙이는 게 아니라 **git 태그로 그 시점의 코드를 고정**해두는 것이 핵심이에요.

## 6. 팀원 한 명의 작업 흐름 (복습)

1. 이슈 확인 (예: `#12 리뷰 이미지 업로드`)
2. 자기 fork에서 브랜치 생성 (`feature/review-image-upload`)
3. 코딩 → 로컬에서 실행해서 확인 (단위 테스트)
4. 커밋 (`Feat: 리뷰 이미지 업로드 구현`) → push
5. PR 생성 → 팀장 리뷰 → Merge
6. 개발일지에 기록

> Git 사용법, 브랜치·커밋·PR 작성 규칙은 **「BinGo Map GitHub 사용 가이드」** 를 참고하세요.
