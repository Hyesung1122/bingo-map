 3-2. 기능별 상세 사양
--------------------------------------------------------------------------------

 [ 지도 ] (완료 - 참고용)

  - Overpass API에서 도톤보리 bounding box 내의
    amenity=waste_basket / amenity=recycling 노드를 조회
  - 카테고리 3분류
      general : 일반쓰레기
      recycle : 재활용
      can     : 캔·병
  - GET /api/bins 로 JSON 반환
    -> map.html 의 JS가 fetch 해서 지도에 마커로 렌더링
  - 검색 / 카테고리 필터 / 목록 UI / 마커 팝업 포함

  ※ 다른 기능들도 이 구조(REST API + JS fetch)를 그대로 따를 것.


 [ 회원 / 인증 ]

  - 이메일 + 비밀번호 기반 가입 및 로그인
  - 로그인 페이지에서만 회원가입 페이지로 진입
    (헤더에 회원가입 버튼 별도로 두지 않음)
  - 소셜 로그인(구글/애플/카카오) 버튼은 UI만 배치, 기능 구현은 범위 외


 [ 즐겨찾기 ]

  - 로그인 사용자가 쓰레기통 또는 맛집을 저장 / 삭제
  - 저장한 목록을 카드 형태로 조회
    (표시 항목 : 이름, 위치, 저장한 날짜)


 [ 리뷰 ]

  - 로그인 사용자가 쓰레기통 또는 맛집에 리뷰 작성
    (별점 1~5 + 텍스트)
  - 대상별 리뷰 목록 조회
  - 본인이 쓴 리뷰만 수정 / 삭제 가능


 [ 주변 맛집 ]

  - 테이크아웃 맛집 목록 및 상세 조회
  - (확장 과제) 쓰레기통 기준 반경 내 맛집 필터링


 [ 공지사항 ]

  - 공지 목록 / 상세 조회
  - 작성·수정·삭제는 관리자(ADMIN) 권한만 가능


--------------------------------------------------------------------------------
 3-3. 범위 외 (이번 단계에서 하지 않음)
--------------------------------------------------------------------------------

  - 소셜 로그인 실제 연동
  - 비밀번호 찾기 메일 발송
  - 경로 안내(/route), 커뮤니티(/community)
  - 다국어 처리 (언어 선택 UI만 존재)
  - 결제, 관리자 페이지

 4. 설계서
================================================================================

--------------------------------------------------------------------------------
 4-1. 아키텍처 계층 구조
--------------------------------------------------------------------------------

      [ View ]        HTML + JS (fetch)
          |
          |  HTTP (JSON)
          v
      [ Controller ]  요청/응답만 담당. 비즈니스 로직 넣지 말 것.
          |
          v
      [ Service ]     비즈니스 로직, 트랜잭션 경계
          |
          v
      [ Repository ]  Spring Data JPA 인터페이스
          |
          v
      [ Entity ]      DB 테이블 매핑
          |
          v
      Oracle DB              + 외부 : Overpass API (지도 기능만 사용)


--------------------------------------------------------------------------------
 4-2. 데이터 설계 - 공통 규칙 (★ 전원 필수 준수 ★)
--------------------------------------------------------------------------------

  1) 모든 Entity 는 BaseEntity 를 extends 할 것
     -> created_at / updated_at 이 자동으로 관리됨
     -> 각자 createDate, regDate 같은 컬럼을 새로 만들지 말 것

  2) PK 는 Long id 로 통일

  3) DB 컬럼명은 snake_case, Java 필드명은 camelCase
     예) created_at  <->  createdAt

  4) WasteBin(쓰레기통)은 테이블로 만들지 않는다
     -> Overpass API 에서 실시간으로 받아오는 데이터이므로 DB 저장 안 함
     -> 즐겨찾기/리뷰에서 쓰레기통을 참조할 때는
        target_id 에 OSM 노드 ID(문자열)를 저장

  5) 즐겨찾기 / 리뷰의 대상 참조는 target_type + target_id 방식
     -> target_type 에 "WASTE_BIN" 또는 "RESTAURANT" 를 넣어 구분
     -> TargetType enum 을 그대로 가져다 쓸 것 (새로 만들지 말 것)

  6) USERS 테이블은 팀장이 먼저 만들어서 main 에 올린다
     -> 팀원 각자 새로 만들지 말고, 올라온 것을 그대로 참조할 것


--------------------------------------------------------------------------------
 4-3. 테이블 명세
--------------------------------------------------------------------------------

 ■ USERS (회원)

  컬럼          타입             제약                     설명
  -----------   --------------   ----------------------   -------------------
  id            NUMBER           PK, 자동증가
  email         VARCHAR2(100)    NOT NULL, UNIQUE         로그인 ID
  password      VARCHAR2(255)    NOT NULL                 암호화 저장
  name          VARCHAR2(50)     NOT NULL                 닉네임
  role          VARCHAR2(20)     NOT NULL, 기본값 USER    USER / ADMIN
  created_at    TIMESTAMP                                 BaseEntity
  updated_at    TIMESTAMP                                 BaseEntity


 ■ FAVORITES (즐겨찾기)

  컬럼          타입             제약                     설명
  -----------   --------------   ----------------------   -------------------
  id            NUMBER           PK
  user_id       NUMBER           FK -> USERS.id, NOT NULL
  target_type   VARCHAR2(20)     NOT NULL                 WASTE_BIN /
                                                          RESTAURANT
  target_id     VARCHAR2(100)    NOT NULL                 OSM 노드 ID 또는
                                                          맛집 PK
  target_name   VARCHAR2(200)                             목록 표시용 캐시
  created_at    TIMESTAMP
  updated_at    TIMESTAMP

  ※ UNIQUE(user_id, target_type, target_id) : 같은 걸 두 번 저장 못하게 함


 ■ REVIEWS (리뷰)

  컬럼          타입             제약                     설명
  -----------   --------------   ----------------------   -------------------
  id            NUMBER           PK
  user_id       NUMBER           FK -> USERS.id, NOT NULL
  target_type   VARCHAR2(20)     NOT NULL                 WASTE_BIN /
                                                          RESTAURANT
  target_id     VARCHAR2(100)    NOT NULL
  rating        NUMBER(1)        NOT NULL, 1~5            별점
  content       VARCHAR2(1000)                            리뷰 본문
  created_at    TIMESTAMP
  updated_at    TIMESTAMP


 ■ RESTAURANTS (맛집)

  컬럼          타입             제약                     설명
  -----------   --------------   ----------------------   -------------------
  id            NUMBER           PK
  name          VARCHAR2(200)    NOT NULL
  category      VARCHAR2(50)                              타코야키,
                                                          오코노미야키 등
  address       VARCHAR2(300)
  latitude      NUMBER           NOT NULL
  longitude     NUMBER           NOT NULL
  image_url     VARCHAR2(300)
  created_at    TIMESTAMP
  updated_at    TIMESTAMP


 ■ NOTICES (공지사항)

  컬럼          타입             제약                     설명
  -----------   --------------   ----------------------   -------------------
  id            NUMBER           PK
  author_id     NUMBER           FK -> USERS.id           작성 관리자
  title         VARCHAR2(200)    NOT NULL
  content       CLOB             NOT NULL
  view_count    NUMBER           기본값 0                 조회수
  created_at    TIMESTAMP
  updated_at    TIMESTAMP


--------------------------------------------------------------------------------
 4-4. 테이블 관계 (ERD 요약)
--------------------------------------------------------------------------------

    USERS  1 ------ N  FAVORITES
    USERS  1 ------ N  REVIEWS
    USERS  1 ------ N  NOTICES        (관리자가 작성)

    RESTAURANTS  1 ------ N  FAVORITES   (target_type=RESTAURANT 인 경우)
    RESTAURANTS  1 ------ N  REVIEWS     (target_type=RESTAURANT 인 경우)

    ※ RESTAURANTS 와의 관계는 DB 가 강제하는 FK 제약이 아니라,
       코드 레벨에서 지켜야 하는 약속임 (target_type 으로 구분).
       쓰레기통(WASTE_BIN)은 테이블이 없으므로 FK 자체가 없음.

 4-5. API 명세 (초안)
--------------------------------------------------------------------------------

 기능            Method   URL                                    요청 파라미터
 --------------  -------  -------------------------------------  ----------------
 쓰레기통 조회   GET      /api/bins                              -

                                                                 name

                                                                 targetId,
                                                                 targetName
 즐겨찾기 삭제   DELETE   /api/favorites/{id}                    -

 [ API 공통 규칙 ]

  - 모든 API 는 JSON 으로 통신
  - API URL 은 반드시 /api/ 프리픽스를 붙인다
  - 페이지 라우팅용 Controller 와 API 용 Controller 는 분리
      예) FavoriteController     -> /favorites 페이지 이동
          FavoriteApiController  -> /api/favorites JSON 응답
  - 조회는 GET, 생성은 POST, 삭제는 DELETE

 5. 개발 단계 계획
================================================================================

 단계   내용                                                      담당
 -----  --------------------------------------------------------  --------
  0     공통 뼈대를 main 브랜치에 선반영                          팀장
        (BaseEntity, TargetType, USERS, @EnableJpaAuditing)
  1     담당 기능의 Entity -> Repository -> Service 작성           팀원
  2     더미 데이터로 화면 동작 확인 (DB 연동 전)                  팀원
  3     Oracle 실제 테이블 생성 및 연동                            팀원
  4     API 연결 및 화면 반영                                      팀원
  5     PR 생성 -> 기능 검증 -> merge                              팀원/팀장


 ★ 중요 ★
  0단계가 끝나기 전에 팀원이 각자 USERS 테이블을 만들면 충돌이 발생합니다.
  0단계 merge 완료 공지를 받은 뒤에 작업을 시작해 주세요.

--------------------------- 여기서부터 복사 ---------------------------

[프로젝트 공통 정보]
- Spring Boot 4.1.1, Java 17, Gradle
- 패키지: com.bingomap.bingo_map
- DB: Oracle Database 11g
- 기존 컨트롤러는 forward 방식이고, 지도 페이지(BinController)는
  /api/bins 로 JSON을 반환하면 map.html의 JS가 fetch로 받아서 화면에
  그리는 구조임. 내가 맡은 기능도 이 방식(REST API + JS fetch)으로
  연동하고 싶음.
- Entity는 반드시 공통 BaseEntity를 extends 해야 하고,
  USERS 테이블 구조와 TargetType enum은 이미 확정된 값이므로
  새로 만들지 말고 그대로 참조할 것.

[내가 맡은 기능]
- 기능 이름: (예: 즐겨찾기)
- 담당 브랜치: (예: feature/favorites)
- 관련 파일:
  - Controller: (파일명 + 내용 붙여넣기)
  - View: (파일명 + 내용 또는 핵심 부분 붙여넣기)

[이 기능에서 다뤄야 할 데이터]
- 어떤 정보를 저장/보여줘야 하는지 최대한 구체적으로:
  (예: 사용자가 특정 쓰레기통이나 맛집을 즐겨찾기에 저장하고,
   즐겨찾기 페이지에서 저장한 목록을 리스트로 보고 싶다.
   각 항목에는 이름, 위치, 저장한 날짜가 보였으면 좋겠다.)

[화면에서 원하는 동작]
- (예: 즐겨찾기 페이지에 들어가면 가짜 데이터라도 3~4개 항목이
   카드 형태로 보였으면 좋겠다. 삭제 버튼을 누르면 목록에서
   빠지는 것도 보고 싶다.)

[0단계 - 코드 작성 전에 먼저]
바로 코드 주지 말고, 먼저 아래를 문서로 정리해서 보여줘.
내가 확인하고 OK하면 그때 코딩 시작.
- 필요한 테이블 목록과 각 컬럼(이름/타입/제약조건)
- 어떤 API 엔드포인트가 필요한지 (URL, 메서드, 요청/응답 형태)
- 기존 USERS 테이블이나 다른 팀원 기능과 겹치는 부분이 있는지

[요청 사항]
1. 이 기능에 맞는 Entity 클래스를 설계해줘 (테이블 구조 포함)
2. Repository, Service 클래스도 같이 만들어줘
3. 실제 DB 연동 전에, 먼저 가짜 데이터(더미 데이터)로 화면에서
   동작하는 걸 보고 싶어. 어떻게 하면 되는지 알려줘
4. 기존 Controller를 수정해서 이 데이터를 View에 연결하는 방법도 알려줘
5. 코드는 한 번에 다 주지 말고, Entity -> Repository -> Service ->
   Controller 순서로 한 단계씩 나눠서 알려줘.
   그리고 왜 이렇게 구성했는지 이유도 같이 설명해줘

[완료 후 처리]
- 다 만들고 나서 어떻게 커밋/브랜치/PR을 올리면 되는지도 마지막에
  알려줘 (내 Fork -> 담당 브랜치 커밋 -> bingo-map/bingo-map 원본으로 PR)

  3) PR 생성 후 팀장에게 보고 -> 기능 검증 진행
  4) 검증 통과 시 팀장이 merge -> 팀 전체가 pull 받아 업데이트

 7. 결정 필요 항목 (팀장 확정 대기)
================================================================================

 아래 항목은 아직 확정되지 않았습니다. 확정되면 이 문서를 갱신합니다.

 1) 인증 방식
    - Spring Security 도입 vs 단순 Session 방식
    - 비전공자 기준 부담을 고려하면 Session + 직접 구현을 권장

 2) 비밀번호 암호화
    - 평문 저장은 검증 시 지적 대상이 됨
    - 최소 BCrypt 적용 권장

 3) 맛집 데이터 출처
    - 현재 메인페이지 맛집 5종은 이미지/이름만 있는 정적 데이터
    - DB 수동 입력 vs Overpass API 로 amenity=restaurant 조회

 4) target_name 캐시 컬럼
    - 즐겨찾기 목록 표시할 때 쓰레기통 이름을 매번 Overpass 에서
      다시 조회하면 느려지므로, 저장 시점의 이름을 함께 저장하도록 설계
    - 정규화 원칙에는 어긋나지만 실용적 선택

 5) DDL 관리 방식
    - 현재 application.yaml 은 ddl-auto: none
    - 개발 단계에서 update 로 두면 Entity 만 만들어도 테이블이 자동
      생성되어 학습에 유리
    - 단, 팀원 각자 로컬 Oracle 사용인지 공용 DB 사용인지에 따라 판단 필요
